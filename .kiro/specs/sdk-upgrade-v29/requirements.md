# Requirements Document

## Introduction

The workspace currently pins `soroban-sdk = "22"` (Cargo major-version pin, resolves to the
latest `22.x` release). The current latest release on crates.io is **v29.0.1**. Seven major
versions separate the contract from the current toolchain, accumulating:

- **Three security advisories** patched in later versions:
  - `GHSA-96xm-fv9w-pf3f` — arithmetic overflow in `Bytes::slice`, `Vec::slice`, and
    `Prng::gen_range(u64)` (fixed in `> 25.0.1`).
  - `GHSA-4chv-4c6w-w254` — `#[contractimpl]` macro calls an inherent function instead of the
    intended trait function when names collide (fixed in a later patch).
  - `CVE-2026-32322` — authentication bypass via crafted scalar field values in cryptographic
    comparisons (fixed in a later release).
- New SDK features not available at v22: `#[contractevent]` typed event macro, improved
  `testutils` auth-testing utilities, Protocol 28 capabilities (CAP-85, CAP-86).
- Accumulating compile-error risk as the Rust toolchain minimum version drifts (v29 requires
  Rust ≥ 1.91.0).

**Target version:** `soroban-sdk = "29.0.1"` (pinned patch version per the pinning policy).

**Scope:** bump the dependency, fix every compile error it introduces, regenerate test
snapshots, document interface changes. Typed-events migration (`#[contractevent]`) is a
separate issue and is **out of scope**.

## Requirements

### Bug Analysis

### Current Behavior (Defect)

1.1 WHEN the workspace `Cargo.toml` specifies `soroban-sdk = "22"` THEN Cargo resolves to
the latest `22.x` release, which is affected by `GHSA-96xm-fv9w-pf3f` (arithmetic overflow
in `Bytes::slice` / `Vec::slice` / `Prng::gen_range`), exposing any enrollment or data range
operation that receives user-controlled bounds to silent data corruption.

1.2 WHEN the workspace `Cargo.toml` specifies `soroban-sdk = "22"` THEN the contract is
affected by `GHSA-4chv-4c6w-w254` (`#[contractimpl]` inherent-vs-trait name collision), which
can cause the wrong function to be called if any impl block has colliding names.

1.3 WHEN the workspace `Cargo.toml` specifies `soroban-sdk = "22"` THEN the contract is
affected by `CVE-2026-32322` (auth bypass via crafted scalar field values), a security risk
for any contract operation that relies on equality checks on user-supplied scalar values.

1.4 WHEN a developer runs `cargo build` against `soroban-sdk = "22"` THEN the minimum
required Rust version diverges from v29's requirement of `>= 1.91.0`, making CI
environments that pin the latest stable Rust unable to reproduce the build exactly.

1.5 WHEN `soroban-sdk = "22"` is in use THEN `#[contractevent]` and the improved `testutils`
mock-auth helpers introduced in later versions are unavailable, forcing event testing to rely
on raw `last_event` / `try_into_val` destructuring rather than typed assertions.

### Expected Behavior (Correct)

2.1 WHEN the workspace `Cargo.toml` specifies `soroban-sdk = "29.0.1"` THEN `cargo build`
and `cargo test` SHALL both succeed with zero errors and zero warnings attributable to the
SDK upgrade.

2.2 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN it SHALL no longer be
affected by `GHSA-96xm-fv9w-pf3f`, `GHSA-4chv-4c6w-w254`, or `CVE-2026-32322`.

2.3 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN the minimum Rust version
SHALL be stated explicitly in the workspace `Cargo.toml` as `rust-version = "1.91.0"` so CI
can enforce it.

2.4 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN all existing test
assertions SHALL continue to pass, including the 323 snapshot files in
`contracts/hamplard/test_snapshots/test/`.

2.5 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN a migration notes
document SHALL be written at `docs/sdk-v29-migration.md` recording every API change observed
during the upgrade so future maintainers understand what changed and why.

2.6 WHEN `soroban-sdk = "29.0.1"` is in use THEN the `stellar contract build` CLI command
SHALL produce a valid Wasm artifact with no warnings about deprecated features.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN the storage model
(all `DataKey` variants, all `DataKey2` variants, all `#[contracttype]` structs and enums)
SHALL be unchanged so deployed state is not invalidated.

3.2 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN every public function
signature (`fn init`, `fn register_course`, `fn enroll`, `fn approve_course`, etc.) SHALL
remain callable with the same argument types and return types as before the upgrade.

3.3 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN all 323 test snapshots
SHALL either be byte-identical to pre-upgrade or SHALL be regenerated by running
`UPDATE_SNAPSHOTS=1 cargo test` and then confirmed stable on a subsequent `cargo test` run.

3.4 WHEN the contract is built against `soroban-sdk = "29.0.1"` THEN the event payload
convention (topics = name + primary ID, data = primary ID + actor + ledger_seq + fields)
documented in `docs/event-conventions.md` SHALL be preserved without modification.

## Glossary

| Term | Definition |
|---|---|
| MSRV | Minimum Supported Rust Version — the oldest Rust release guaranteed to compile the crate. |
| Pin | Specifying an exact version string (e.g. `"29.0.1"`) rather than a range (`"22"`), so `cargo update` cannot silently advance the version. |
| Snapshot | JSON file in `test_snapshots/test/` capturing ledger state and auth traces for a test scenario, used by the Soroban test framework for regression detection. |
| CVE | Common Vulnerabilities and Exposures identifier — a public security advisory record. |
| SAC | Stellar Asset Contract — the built-in token contract interface exposed via `soroban_sdk::token::Client`. |
| Protocol version | The Stellar network protocol number (e.g. 22, 28) that the SDK major version tracks. SDK v29 targets Protocol 29. |
